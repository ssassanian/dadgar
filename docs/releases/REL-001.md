## ۲) استاندارد و معماری خروجی

- بک‌اند: همان منطق امن فاز ۱ و ۲ (پورت وفادار از `dadgar/server.js`) — **فایل مرجع اصلی بدون تغییر باقی مانده است**
- ورودی‌های سرورلس: `web/api/[[...path]].js` (API)، `web/api/html.js` (صفحه با CSP nonce)، `web/api/notfound.js` (۴۰۴)
- لایه دیتابیس: `web/lib/db.pg.js` — همان سطح تماس کد اصلی روی Postgres
- فرانت‌اند: `dadgar/public/index.html` — **عیناً بدون تغییر** (در `web/dynamic/` قرار گرفته و با nonce سرو می‌شود)
- امنیت (تست‌شده روی production): CSP سخت‌گیر با nonce، `__Host-sid` + HttpOnly + SameSite=Strict + Secure، HSTS، CSRF دو لایه، قفل تلاش ناموفق ماندگار، رمزنگاری AES-256-GCM شماره تلفن، scrypt + pepper، Audit Log، محدودکننده نرخ (مهاجرت‌یافته به جدول `rate_limits`)
- محدودیت شناخته‌شده (مستند): پیامک فعلاً درایور `console` است (کد OTP در لاگ توابع Vercel دیده می‌شود)؛ پس از تهیه پنل پیامک، طبق README خود پروژه `SMS_DRIVER=http` تنظیم می‌شود (کار فاز بعد با تایید مدیر)

## ۳) کلید و امضا (طبق قانون Release)

- دفتر کلیدها: [`docs/releases/keys-register.txt`](keys-register.txt)
- `APP_SECRET` (مشتق‌کننده همه کلیدهای رمزنگاری): در Env Variables پروژه Vercel (encrypted) + بکاپ محلی نزد مدیر. **عمداً روی گیت‌هاب کامیت نمی‌شود** — هر کسی که مخزن/توکن را ببیند می‌تواند کل داده‌ها را رمزگشایی کند. تصمیم نهایی درباره نگهداری بکاپ مقدار کلید با مدیر است.
- role دیتابیس `dadgar_app` (کم‌دسترسی): رمز فقط در `DATABASE_URL` پروژه Vercel (encrypted) + بکاپ محلی. دسترسی anon/authenticated صریحاً REVOKE شده است.
- توکن‌های دسترسی (GitHub / Vercel / Supabase): نزد مدیر — در مخزن کامیت نمی‌شوند.
- کلید امضای اپ موبایل (اندروید/iOS): هنوز خروجی موبایلی وجود ندارد؛ در اولین خروجی موبایل طبق قانون Release ثبت و شماره‌گذاری خواهد شد.
