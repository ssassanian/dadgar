## ۲) محتوای خروجی

- **اقدام انتظاری واحدِ REL-009 بسته شد**: DDL جدول `settings` با Supabase Management API اعمال شد (CREATE TABLE + GRANT کامل برای `dadgar_app`) — جدول شانزدهمِ دیتابیس
- **کشف و رفع ایراد زیرساختی (ایده‌ی کلیدی این خروجی)**: Supabase روی جدولِ تازه‌ساخته RLS را پیش‌فرض روشن می‌کند؛ اولین PUT واقعی با خطای `42501` (نقض سیاست RLS) شکست خورد — در حالت degrade قبلی هرگز آزمایش نشده بود. رفع: `ALTER TABLE settings DISABLE ROW LEVEL SECURITY` — هم‌سویی با هر ۱۵ جدول مرجع (`rowsecurity:false` برای همه)؛ مدل امنیتی پروژه در لایه‌ی API است (CSRF/نرخ/نقش — CMD-002/ACT-006). فایل `web/db/settings-pending-ddl.sql` نیز با خط ALTER به‌روزرسانی شد تا بازتولید رویه در آینده همین مشکل را نداشته باشد
- **فعال‌سازی بدون تغییر کد**: `/api/settings/public` از `ready:false` به `ready:true` تغییر کرد و مسیر نوشتن از 503 صادقانه به «تنظیمات ذخیره شد» — دقیقاً مطابق مکانیسم degrade شفاف CMD-010، بدون هیچ دیپلوی جدید
- **تست نهایی جامع پس از تغییر وضعیت دیتابیس** (بند ۴) — شامل اولین تست کامل چرخه‌ی نوشتن settings (PUT → GET → public → audit → upsert)
- بدون تغییر در فایل مرجع `dadgar/`؛ بدون تغییر در `web/lib/web.js` و صفحات تزریق‌شده
