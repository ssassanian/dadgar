## محدوده‌ی دقیق اجرا (مطابق قانون عمومی — فقط همین)

**۸ صفحه از حالت نمایشی خارج و به دیتابیس وصل شد:**

| صفحه | پنل | نتیجه |
|---|---|---|
| ثبت پرونده جدید (`cNew`) | مشتری | ویزارد ۴ مرحله‌ای حفظ شد؛ «تایید نهایی» واقعاً در جدول `cases` ثبت می‌کند |
| پرونده‌های من (`cCases`) | مشتری | فهرست واقعی پرونده‌های خود کاربر + صفحه‌بندی سرور |
| پرونده‌های باز (`lOpen`) | وکیل | پرونده‌های `waiting/proposing` بدون مشخصات مشتری + خلاصه |
| ارسال/ویرایش پیشنهاد (`lProp`) | وکیل | فرم واقعی مبلغ/مدت/یادداشت خصوصی؛ ویرایش پیشنهاد در انتظار |
| پیشنهادهای من (`lProps`) | وکیل | فهرست واقعی + ویرایش + حذف (با بازگشت وضعیت پرونده) |
| پرونده‌های تخصیص‌یافته (`lCases`) | وکیل | پرونده‌های `lawyer_id=خودم` |
| مدیریت پرونده‌ها (`aCases`) | مدیر | فهرست کل + نام مشتری |
| جزئیات پرونده (`aCase`) | مدیر | اطلاعات کامل + قیمت نهایی + جدول پیشنهادهای وکلا + تایید پیشنهاد (اتمیک) |

**صفحاتی که عمداً در این گام وصل نشدند** (گام‌های بعدی برنامه): `cCase`/`lCase` (تب‌های مدارک/پیام‌ها/صورتحساب = گام‌های ۲ به بعد)، داشبوردها، نوبت‌دهی، مالی، نظرات، پیام‌ها/تیکت‌ها، اسناد، لاگ، CMS/تنظیمات/سئو. صفحات جزئیات مشتری/وکیل همچنان نوار زرد «بخش نمایشی» دارند.

## APIهای جدید (۹ مسیر — همه با همان لایه‌های امنیتی فاز ۱: نشست، CSRF، نقش، نرخ، پارامتری)

| مسیر | نقش | کار |
|---|---|---|
| `GET /api/cases` (+`scope=open/mine`، `page`) | هر سه نقش | فهرست نقش‌محور با صفحه‌بندی (۱۰ در صفحه) |
| `POST /api/cases` | مشتری | ثبت پرونده (`waiting`) — سقف ۵ در ساعت |
| `GET /api/cases/:id` | با کنترل دسترسی | جزئیات؛ مشتری/مدیر متن کامل، وکیلِ غیرمسئول فقط خلاصه ۱۶۰ نویسه |
| `PATCH /api/cases/:id` | مدیر | ثبت قیمت نهایی |
| `POST /api/cases/:id/proposals` | وکیل | ثبت پیشنهاد (یکتا per وکیل/پرونده) — وضعیت پرونده `waiting→proposing` |
| `GET /api/proposals` | وکیل | پیشنهادهای خودم |
| `PATCH /api/proposals/:id` | وکیل | ویرایش پیشنهاد در انتظار |
| `DELETE /api/proposals/:id` | وکیل | حذف پیشنهاد در انتظار (آخرین پیشنهاد → پرونده به `waiting` برمی‌گردد) |
| `POST /api/proposals/:id/accept` | مدیر | **تراکنش اتمیک:** تایید یکی، رد خودکار بقیه، تخصیص وکیل + `final_price` + وضعیت `assigned` |

## امنیت و حریم خصوصی (طبق README خود پروژه)

- **AES-256-GCM**: متن توضیحات پرونده (`description_enc`, AAD `case.description`) و یادداشت خصوصی پیشنهاد (`note_enc`, AAD `proposal.note`) — اولین استفاده‌ی واقعی از این الزام README
- **حریم خصوصی مشتری**: وکیل هرگز نام/شماره مشتری را نمی‌بیند (فقط خلاصه)؛ شماره تماس حتی برای مدیر ماسک‌شده است (`0•••••1234`)
- **404 به‌جای 403** برای پرونده‌ی غیرمجاز (بدون افشای وجود)
- Audit Log: `case_create`, `case_final_price`, `proposal_create/edit/delete/accept`
- فایل مرجع `dadgar/` همچنان **دست‌نخورده**؛ همه‌ی تغییرات در لایه `web/` (الگوی CMD-002). تزریق فرانت‌اند از فایل مرجعِ دست‌نخورده بازتولید می‌شود (`scripts/inject-cycle.py`)

## وضعیت‌های پرونده (عیناً از اسکیمای مرجع)

`waiting` (در انتظار بررسی) → `proposing` (در حال پیشنهاد) → `assigned` (تخصیص‌یافته) → `running` (در حال انجام — گام بعدی) → `done` (بسته‌شده — گام بعدی)
