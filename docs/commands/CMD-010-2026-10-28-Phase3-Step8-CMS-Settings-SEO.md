## متن دستور (رونوشت عینی)

> «ادامه کارهای مانده و تست نهایی»

**تفسیر ثبت‌شده (شفاف و قابل ردگیری):** همان دستور CMD-009 — «کارهای مانده» = گام‌های ۷ و ۸ توالی مصوب؛ گام ۷ (لاگ مدیر) با REL-008 منتشر شد. این سند اجرای **گام ۸ (آخرین گام توالی)** است. «تست نهایی» = تست جامع پایانی همه‌ی ماژول‌ها که به‌عنوان دروازه‌ی خروجی REL-009 اجرا و مستند می‌شود (هر ۸ سوییت API + همه‌ی e2e مرورگر + رگرسیون زنده‌ی production).

## تصمیم طراحی جدول (نقطه‌ای که پیش‌تر «نیازمند تصمیم مدیر» ثبت شده بود)

اسکیمای مرجع (SQLite سندشده در `dadgar/lib/db.js`) **هیچ جدولی برای CMS/تنظیمات ندارد** — پورت وفادار هم نمی‌تواند از خودش جدول بسازد. طبق دستور «ادامه‌ی کارهای مانده»، حداقلی‌ترین طراحی هم‌سو با اصول پروژه (پارامتری، بدون تغییر جدول‌های مرجع، بدون کلید در مخزن) انتخاب و **به‌عنوان افزوده‌ی ثبت‌شده (نه پورت مرجع)** مستند شد:

```sql
-- CMD-010 — افزوده‌ی ثبت‌شده (مرجع جدول تنظیمات ندارد)
CREATE TABLE IF NOT EXISTS settings(
  key TEXT PRIMARY KEY,
  value TEXT,
  updated_at BIGINT NOT NULL,
  updated_by BIGINT REFERENCES users(id)
);
```

- مدل **key-value سفید‌لیست‌شده**: فقط کلیدهای اعلام‌شده در سرور پذیرفته می‌شوند (`site_phone, site_email, site_address, site_instagram, site_telegram, tariff_phone, tariff_meeting, tariff_contract`) — هر کلید ناشناخته 400
- سقف طول هر مقدار در سرور (۱۰۰ تا ۵۰۰ کاراکتر بر اساس نوع)؛ پارامتری کامل؛ Audit با رویداد `settings_save`
- **بدون تغییر در ۱۵ جدول مرجع** — `settings` جدولی متمایز و مستقل است

## محدوده‌ی دقیق اجرا (مطابق قانون عمومی — فقط همین)

1. **`aSet`** (`/a/settings`): تب «تنظیمات سایت» واقعی — ذخیره‌ی ۵ فیلد تماس (تلفن/ایمیل/نشانی/اینستاگرام/تلگرام)؛ پیش‌پرشدن از DB با مقادیر پیش‌فرض مرجع
2. **`aCms`** (`/a/cms`): تب «تعرفه‌ها» واقعی — ذخیره‌ی ۳ تعرفه و نمایش زنده‌ی آن‌ها در صفحه‌ی عمومی «تعرفه‌ها» (`/pricing`) با override کنترل‌شده (الگوی CMD-006) و fallback به مقادیر مرجع
3. **`aSeo`** (`/a/seo`): ثبت به‌مثابه صفحه‌ی واقعی (`VR.aSeo=V.aSeo`) — این صفحه «سند برنامه‌ریزی» است (خودش تصریح می‌کند رتبه‌بندی «پیشنهاد مدیریتی اولیه» است نه داده‌ی دینامیک) و هیچ دکمه/داده‌ی نمایشی جعلی ندارد؛ فقط نوار زرد برداشته می‌شود
4. سه مسیر API جدید + اعمال DDL جدول `settings` روی Supabase
5. بدون تغییر در فایل مرجع `dadgar/`

## بخش‌هایی که آگاهانه نمایشی می‌مانند (با پیام صادقانه — نیازمند تصمیم بعدی مدیر)

| بخش | دلیل ثبت‌شده |
|---|---|
| `aCms` صفحات ثابت (درباره/تماس/سوالات) | ویرایش محتوای غنی صفحات عمومی نیازمند طراحی ویرایشگر و مکان درج در ویوهای مرجع است |
| `aCms` مقالات | مقالات محتوای ساختاریافته‌ی مرجع‌اند؛ پویاسازی نیازمند جدول محتوا و تغییر صفحات عمومی است |
| `aCms` دسته‌بندی‌ها | `CATS` قرارداد اعتبارسنجی سمت سرور ثبت پرونده است؛ پویاسازی بدون همگام‌سازی بک‌اند، داده‌ی ناسازگار می‌سازد |
| `aSet` دسترسی نقش‌ها | ماتریس دسترسی پویا نیازمند لایه‌ی مجوز جدید در همه‌ی ۴۳ مسیر است |
| `aSet` لوگو | آپلود فایل نیازمند انبار شیء (تصمیم باز CMD-008) |

## APIهای جدید (۳ مسیر — لایه‌های امنیتی فاز ۱: نشست/CSRF/نقش/نرخ/پارامتری)

| مسیر | نقش | شرح |
|---|---|---|
| `GET /api/settings` | admin | همه‌ی تنظیمات (`map` + آخرین `updated_at`) |
| `PUT /api/settings` | admin | ذخیره‌ی دسته‌ای با سفید‌لیست کلید + سقف طول + Audit `settings_save` |
| `GET /api/settings/public` | مهمان | زیرمجموعه‌ی عمومی (اطلاعات تماس + تعرفه‌ها) برای صفحات عمومی |

جمع مسیرهای API: **۴۶** (۴۳ + ۳).

## تست‌ها
