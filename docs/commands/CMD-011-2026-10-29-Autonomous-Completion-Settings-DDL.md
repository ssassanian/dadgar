## متن دستور (رونوشت عینی)

> «خودت انجام بده»

**همراه دستور:** مدیر سه توکن دسترسی ارسال کرد — GitHub PAT (مخزن `ssassanian/dadgar`)، Vercel (دیپلوی)، Supabase (مدیریت پروژه `oyoywxgudbqmptwkxzpi`). مقادیر توکن‌ها **هرگز در مخزن ثبت نمی‌شوند** (طبق قانون عمومی — فقط محلی و خارج از مخزن استفاده شد).

**تفسیر ثبت‌شده (شفاف و قابل ردگیری):** این دستور مجوز اجرای خودکار **اقدام انتظاری واحدِ** ثبت‌شده در ACT-035/REL-009 است — «اعمال `web/db/settings-pending-ddl.sql` توسط مدیر» که به‌دلیل نداشتن دسترسی CREATE برای نقش `dadgar_app` معلق بود. توکن Supabase دقیقاً همین دسترسی ممتاز را فراهم کرد. «انجام بده» شامل بستن چرخه‌ی آن اقدام (تست ماژول تنظیمات در حالت فعال) و تکرار **تست نهایی جامع** همه‌ی ماژول‌ها پس از تغییر وضعیت دیتابیس است.

## محدوده‌ی دقیق اجرا (مطابق قانون عمومی — فقط همین)

1. اعمال DDL جدول `settings` روی Supabase (پروژه `dadgar`) با Management API — CREATE TABLE + GRANT برای `dadgar_app`
2. رفع ایراد کشف‌شده حین تست: Supabase روی جدول جدید RLS را پیش‌فرض روشن می‌کند → خطای `42501` در INSERT → `ALTER TABLE settings DISABLE ROW LEVEL SECURITY` (هم‌سویی با ۱۵ جدول مرجع که RLS خاموش دارند؛ مدل امنیتی پروژه در لایه‌ی API است)
3. به‌روزرسانی `web/db/settings-pending-ddl.sql` با خط ALTER (تا بازتولید رویه در آینده درست باشد)
4. تست نهایی جامع: هر ۸ سوییت API + هر ۸ سوییت e2e مرورگر روی دیتابیس واقعی
5. پاکسازی کامل ردپای تست + تست زنده‌ی production
6. بدون تغییر در فایل مرجع `dadgar/`؛ بدون تغییر کد اپلیکیشن (`web/lib/web.js`) — مطابق طراحی CMD-010، فعال‌سازی صرفاً با اعمال DDL رخ داد

- جدول `settings` فعال شد؛ `/api/settings/public` از `ready:false` به `ready:true` تغییر کرد **بدون هیچ دیپلوی جدید** (دقیقاً مطابق پیش‌بینی ACT-033)
- تست نهایی جامع: **۸/۸ سوییت API + ۸/۸ سوییت e2e — همه موفق**
