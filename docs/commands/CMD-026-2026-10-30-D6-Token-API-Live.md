## ۱) قرارداد پیاده‌شده — عین DOC-04 §۵-۲

| مسیر | ورودی | خروجی | نکته |
|---|---|---|---|
| `POST /api/auth/token` | `{username, password, device?}` — همان حساب‌های موجود وب (نام کاربری یا شماره تماس) | `{ok, token_type:'Bearer', access_token, refresh_token, expires_in:900, user}` | همان throttle ورود وب (کاربر + IP، قفل نمایی)؛ رمز غلط → 401 «نام کاربری یا رمز عبور اشتباه است.» عین وب |
| `POST /api/auth/token/refresh` | `{refresh_token}` | جفت تازه (چرخش) | refresh قبلی و همه‌ی accessهای وابسته به آن باطل می‌شوند؛ سقف مستقل ۶۰/۱۰دقیقه |
| `POST /api/auth/token/revoke` | `{refresh_token, scope:'device'}` (عین کلاینت موبایل) یا `{scope:'all'}` با Bearer، یا فقط Bearer | `{ok:true}` | خروج همان دستگاه با refresh بدنه یا Bearer؛ پاسخ یکسان با/بی توکن معتبر (بدون افشا) |

- **عمر توکن‌ها**: access **۱۵ دقیقه** (انقضای مطلق، بدون idle) + refresh **۳۰ روز** (چرخشی) — دقیقاً مطابق §۵-۲
- **پذیرش Bearer**: در دیسپچر مرکزی — نشست کوکی اول، در نبود آن Bearer؛ یعنی همه‌ی مسیرهای `auth:true` (appointments/cases/invoices/tickets/threads/messages/documents/…) هم‌زمان پذیرای موبایل شدند بدون تغییر تک‌تک آن مسیرها
- **CSRF**: لایه‌ی ۱ (Origin/sec-fetch-site) سر جای خود؛ لایه‌ی ۲ (x-csrf-token) فقط برای نشست کوکی معنا دارد — درخواست Bearer کوکی ندارد و از آن گذر می‌کند (تست e2e بند ۳-گ)
- **ذخیره‌سازی**: جدول `sessions` موجود + ستون جدید `kind` — `'web'` (پیش‌فرض) / `'api-access'` / `'api-refresh'`؛ refresh فقط به‌صورت `sha256` ذخیره می‌شود (عین الگوی نشست وب)؛ پیوند access↔refresh در ستون `csrf` ردیف access (در نشست API بی‌استفاده)

## ۳) راستی‌آزمایی

### ۳-۱) DDL روی دیتابیس واقعی (REL-011)

- وارسی فقط‌خواندنی: `public.sessions` = ۸ ستون اسکیمای مرجع، `relrowsecurity=false` (برخلاف جدول تازه CMD-010، نیازی به DISABLE RLS نبود)
- اعمال: `ALTER TABLE public.sessions ADD COLUMN IF NOT EXISTS kind TEXT NOT NULL DEFAULT 'web'` با Supabase Management API
- اثر بر ردیف‌های موجود: ۴ نشست وب موجود خودکار `'web'` شدند — **صفر شکستگی**؛ دیپلوی فعلی بدون تغییر کد به کار خود ادامه می‌دهد (کد قدیمی ستون را نمی‌شناسد و INSERT‌هایش بدون kind با DEFAULT پر می‌شود)

### ۳-۲) سوییت e2e توکن — `web/scripts/e2e-token.py` (۲۰/۲۰ سبز)

ورود وب (رگرسیون trim) · رمز غلط 401 عین پیام · صدور جفت با قرارداد موبایل (access/refresh/Bearer/expires_in=900) · Bearer روی me/appointments/cases/invoices · نوشتن با Bearer بدون CSRF · چرخش refresh · مرگ access و refresh قدیمی پس از چرخش (401 روی مسیر auth:true) · revoke دستگاه با بدنه · revoke دستگاه با Bearer · نشست وب دست‌نخورده · `/api/me` مهمان 200 (طراحی موجود) — **بهداشت: پس از تست صفر ردیف api باقی ماند**

### ۳-۳) رگرسیون مرورگری — `web/scripts/e2e-book.py` (سبز کامل)

چرخه‌ی کامل نوبت‌دهی با Playwright روی کد جدید: رزرو مشتری ← اشغال بازه ← نمای ناشناس وکیل ← تایید مدیر ← لغو — یعنی مسیر تغییریافته‌ی `startSession` (ورود کوکی) و دیسپچر بدون هیچ رگرسیون

### ۳-۴) گیت موبایل (بدون تغییر کد)

## ۴) کشف‌های ثبت‌شده

1. **`/api/me` همیشه 200 است** (مهمان هم `{user:null}` — «guests get 200 so the browser console stays clean»): ادعای 401 در تست باید روی اندپوینت `auth:true` انجام شود نه `/api/me`. حین دیباگ با dump مستقیم دیتابیس اثبات شد که چرخش refresh درست کار می‌کرده و فقط تست اشتباه بود
2. **باگ واقعی در نسخه‌ی اول revoke با Bearer** (خودم، پیش از کامیت): `sess.csrf=''` پیوند refresh را گم می‌کرد و شاخه‌ی revoke بی‌بدنه عملاً چیزی حذف نمی‌کرد — رفع: `bearerSession` اکنون `refreshId` (مقدار ستون csrf ردیف access) را حمل می‌کند و revoke با آن refresh همان دستگاه را ابطال می‌کند؛ تست اختصاصی اضافه شد
3. **بهینگی ابزار**: در اجرای دستی، بسط `${DBPASS}` داخل همان دستورِ `export` پیش از مقداردهی رخ می‌دهد (خروجی خالی → خطای 28P01) — اسکریپت‌های `.sh` الگوی موجود (export در خط جدا) عیناً درست‌اند

## ۵) امنیت

- توکن‌ها تصادفی ۳۲بایتی (base64url) و فقط به‌صورت sha256 در دیتابیس — افشای DB ≠ افشای نشست
- همان قفل ورود وب (۵ بار کاربر / ۲۵ بار IP با پس‌رفت نمایی) شامل مسیر توکن هم می‌شود — جدا شدن مسیر حمله ممکن نیست
- انقضای مطلق access (۱۵ دقیقه) + چرخش refresh با ابطال زنجیره (روتیشن = مرگ همه‌ی accessهای وابسته)
- audit_log: `login(mobile-token)` / `token_refresh` / `token_revoke(device|all)` — قابل پیگیری در لاگ مدیر
- egress صفر: هیچ secret جدید در کد/مخزن نیست؛ DDL فایل فقط SQL است
