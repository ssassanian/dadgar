## محدوده‌ی دقیق اجرا (مطابق قانون عمومی — فقط همین)

**۲ صفحه از حالت نمایشی خارج و به دیتابیس وصل شد:**

| صفحه | پنل | نتیجه |
|---|---|---|
| صورتحساب‌ها و پرداخت (`cBill`) | مشتری | فهرست واقعی فاکتورهای خودش (شماره، تاریخ شمسی، مبلغ، وضعیت) از `invoices`؛ حالت خالی صادقانه «هنوز فاکتوری برای شما صادر نشده است» |
| مدیریت مالی (`aFin`) | مدیر | ۳ آمار واقعی (درآمد این ماه / فاکتور در انتظار / پرداخت‌های امروز) + جدول همه‌ی فاکتورها با نام مشتری و نام وکیل (وکیل از پرونده‌ی متصل) + فیلتر دوره (این ماه/سه ماه/امسال) + فیلتر وکیل + **صدور فاکتور دستی** (انتخاب مشتری واقعی + مبلغ) + **ثبت پرداخت** و **بازکردن** فاکتور |

**مکانیزم فرانت**: `web/scripts/inject-bill.py` همیشه از فایل مرجعِ دست‌نخورده شروع می‌کند و زنجیره‌ی بلاک‌ها را تزریق می‌کند (CMD-003 ← CMD-004 ← CMD-005؛ اجرای مکرر idempotent). چهار هندلر واقعی جدید (`[data-bpd]` فیلتر دوره، `[data-bpay]` ثبت پرداخت، `[data-bropen]` بازکردن، `[data-billm]` صدور فاکتور) با پیش‌دستی `!DEMO` قبل از هندلرهای نمایشی مرجع درج شدند — برای دومین بار الگوی «پیش‌دستی هندلر» (پس از CMD-004) استفاده شد.

## APIهای جدید (۴ مسیر — همه با همان لایه‌های امنیتی فاز ۱: نشست، CSRF، نقش، نرخ، پارامتری)

| مسیر | نقش | کار |
|---|---|---|
| `GET /api/invoices` | مشتری/مدیر (وکیل 403) | مشتری: فاکتورهای خودش (بدون نام‌ها)؛ مدیر: همه + `client_name` و `lawyer_name` (JOIN از طریق `case_id`) + `today_d` برای محاسبات «امروز» |
| `POST /api/invoices` | مدیر | صدور دستی: `{client_id, amount, case_id?}` — مشتری باید role=client باشد (404 «مشتری یافت نشد»)، مبلغ ۱۰۰۰..۱۰ میلیارد تومان، `case_id` اختیاری فقط اگر پرونده متعلق به همان مشتری باشد (400 در غیر این‌صورت) — سقف ۳۰ صدور در ساعت |
| `PATCH /api/invoices/:id` | مدیر | گذارهای وضعیت: `pending→paid` (ثبت پرداخت، `paid_at=now`) و `paid→pending` (بازکردن برای اصلاح خطا، `paid_at=NULL`) — گذار نامعتبر 400، فاکتور ناموجود 404 بدون افشا |
| `GET /api/users?role=client\|lawyer` | مدیر | فهرست **حداقلی** کاربران فقط برای select فرم صدور فاکتور: `id, name, role, created_at` — بدون تلفن/ایمیل/نام‌کاربری/هش رمز (تست خودکار نشت فیلد دارد) |

## مدل داده و تصمیم‌های ساده‌سازی

- **بدون تغییر اسکیما**: همه‌ی ستون‌های موردنیاز در `invoices` از قبل بود (`id, case_id, client_id, amount, status, created_at, paid_at`) — فاکتور دستی `case_id=NULL` ذخیره می‌شود.
- **مرزهای دوره‌ی شمسی** (ثابت تهران UTC+3:30، هماهنگ با `BK_MONTH_START` گام قبل): «این ماه» = آبان ۱۴۰۵، «سه ماه» = از مهر ۱ (−۳۰ روز)، «امسال» = از فروردین ۱ ۱۴۰۵. فیلتر دوره/وکیل روی ردیف‌های بارگذاری‌شده (سقف ۳۰۰) سمت کلاینت اعمال می‌شود — الگوی صفحه‌بندی/فیلتر مرجع.
- **آمارها**: «درآمد این ماه» = جمع `amount` فاکتورهای `paid` با `paid_at` در آبان؛ «فاکتور در انتظار» = شمارش `pending`؛ «پرداخت‌های امروز» = شمارش `paid` با `paid_at` از ابتدای امروز تهران. (نمایش م.ت = میلیون تومان با یک اعشار فارسی)
- درآمد/وضعیت فقط از داده واقعی می‌آید — هیچ عدد نمایشی جعلی در صفحه مدیر باقی نماند.

## تصمیمات طراحی که برای مدیر ثبت می‌شود (در این گام عمداً انجام نشد)

1. **اتصال درگاه پرداخت آنلاین**: دکمه «پرداخت آنلاین» مشتری فعلاً با پیام صادقانه «درگاه پرداخت هنوز متصل نشده است؛ پس از تصمیم مدیر فعال می‌شود» نمایش داده می‌شود. انتخاب درگاه (زرین‌پال/…)، وب‌هوک و ثبت تراکنش نیازمند تصمیم و دستور مدیر است.
2. **خروجی PDF/اکسل**: دکمه‌های «دانلود PDF» فاکتور و «اکسل/PDF» گزارش مدیر با پیام صادقانه نمایشی ماندند — تولید فایل نیازمند تصمیم مدیر (کتابخانه/قالب).
3. **ستون «شرح/عنوان فاکتور»**: در اسکیمای مرجع وجود ندارد؛ فرم صدور دستی = مشتری + مبلغ. افزودن ستون = تغییر اسکیما که بدون دستور مدیر انجام نمی‌شود. همین‌طور UI «اتصال فاکتور به پرونده» در فرم (API از الان `case_id` را می‌پذیرد).
4. **فاکتور خودکار**: صدور خودکار فاکتور هنگام تایید پیشنهاد (مبلغ پیشنهاد) در UI مرجع وجود ندارد و انجام نشد — در صورت صلاحدید مدیر در گام‌های بعد قابل افزودن است.

## امنیت و حریم خصوصی

- وکیل به API مالی دسترسی ندارد (403) — صفحه مالی وکیل در UI مرجع هم وجود ندارد.
- مشتری فقط فاکتورهای خودش را می‌بیند؛ نام مشتری/وکیل فقط در پاسخ مدیر می‌آید.
- `GET /api/users` فقط شناسه/نام/نقش/تاریخ‌عضویت می‌دهد (حداقل داده برای فرم مدیر) — نشت شماره تلفن/ایمیل/هش رمز با تست خودکار پوشش داده شد.
- CSRF روی POST/PATCH الزامی، سقف نرخ ۳۰ صدور/ساعت برای مدیر + سقف کلی ۳۰۰ درخواست/دقیقه IP، همه‌ی پرس‌وجوها پارامتری، `amount` با whitelist بازه‌ای.
- Audit: `invoice_create` / `invoice_mark_paid` / `invoice_reopen` با user و IP.

## تست‌ها (روی دیتابیس واقعی Supabase — قبل از دیپلوی)

- **API** (`web/scripts/test-bill.sh`): ۱۴ گروه — فهرست خالی + sanity ساعت، 403 وکیل، فهرست حداقلی کاربران (بدون نشت فیلد)، منفی‌های صدور (client_id صفر، مبلغ کم، مشتری ناموجود 404، مدیر به‌جای مشتری 404، ناهمخوانی پرونده 400)، صدور دو فاکتور دستی، نمای مشتری (فیلدها + حریم خصوصی)، نمای مدیر (نام‌ها)، اتصال فاکتور به پرونده‌ی واقعی از چرخه‌ی گام ۱ (ثبت پرونده ← پیشنهاد وکیل ← تایید مدیر ← فاکتور با `lawyer_name` واقعی)، گذارهای PATCH (403 مشتری/وکیل، 400 وضعیت نامعتبر/تکرار/بازکردن پرداخت‌نشده، 404)، امنیت (بدون CSRF 403، مهمان 401)، شمارش Audit — همه موفق.
- **مرورگر واقعی** (`web/scripts/e2e-bill.py` با Playwright): ۶ مرحله — صفحه واقعی مدیر بدون نوار زرد با select پرشده از دیتابیس، صدور فاکتور از فرم واقعی (ردیف با نام مشتری و چیپ «در انتظار» و مبلغ ارقام فارسی)، ثبت پرداخت (چیپ «پرداخت‌شده» + آمار درآمد غیرصفر + دکمه بازکردن)، فیلتر دوره روی داده واقعی، بازکردن به «در انتظار»، نمای مشتری (فاکتور واقعی + دکمه‌های صادقانه + بدون عملیات مدیر) — همه موفق، **بدون خطای JS**.
- ایرادهای حین تست (لایه تست، نه کد محصول): پرانتز بسته‌نشده در بلاک تزریق (قبل از هر تستی با `node --check` گرفته شد)، انتظار `visible` به‌جای `attached` برای `<option>` در Playwright، مقایسه‌ی رشته‌ای COUNT (ادامه‌ی الگوی شناخته‌شده).
- پاکسازی کامل: ۳ کاربر آزمایشی، پرونده/پیشنهاد تست (از چرخه)، فاکتورها، نشست‌ها و کلیدهای نرخ حذف شدند — `invoices left: 0`.
