## متن دستور (رونوشت عینی)

> «من فکر کنم ما یک اشتباه فنی کرده ایم و باید اینو درست کنیم ---- اینو بررسی کن --- **پیشنهاد کوتاه:** دو ریپوی جدا برای «موبایل» و «وب» نسازید. بک‌اند و API باید جدا و مشترک باشد، و بهترین شروع برای تیم کوچک **یک مونوریپو** است. ... [متن کامل پیشنهاد ۵ بخشی: ساختار مونوریپو با apps/mobile, apps/web, apps/admin, services/api, packages/api-contract, packages/design-tokens, packages/shared-i18n, infra؛ جدول نیتیو/چندسکویی؛ وب و پنل‌ها؛ مقیاس‌پذیری؛ روند کار تیم] ... تیم‌تان چه زبان‌هایی بلد است؟»

پیشنهاد مذکور یک نظرخواهی فنی خارجی است که مدیر برای ارزیابی مستقل ارسال کرد.

## تفسیر ثبت‌شده

1. **درخواست بررسی فنی بلاتعارض** — نه تایید خودکار و نه رد خودکار پیشنهاد
2. **صفر کدنویسی** تا تصمیم مدیر پس از خواندن این بررسی (همان الگوی CMD-012)
3. پاسخ به ادعای «اشتباه فنی» باید مبتنی بر اسناد مصوب و وضعیت واقعی پروژه باشد

## بررسی نقطه‌به‌نقطه

### ۱) پیش‌فرض اصلی پیشنهاد در دادگر **از قبل برقرار است**

بند اول پیشنهاد می‌گوید: «بک‌اند و API باید جدا و مشترک باشد». وضعیت واقعی دادگر:

- **بک‌اند = Supabase** (مدیریت‌شده، کاملاً خارج از هر دو مخزن): Postgres + RLS + REST نسخه‌بندی‌شده — نه در ریپوی وب است نه موبایل
- **دو مخزن فعلی فقط دو «کلاینت»‌اند** (وب = serverless/Vercel؛ موبایل = Flutter) و تنها رابط بین‌شان همان API است = **دقیقاً همان فلسفه‌ی پیشنهاد**
- تفاوت واقعی فقط این است که کد دو کلاینت در یک گیت‌ریپو باشد یا دو گیت‌ریپو — یعنی موضوع «سلیقه/گردش‌کار تیمی»، نه «معماری درست/غلط»

### ۲) معیار خودِ پیشنهاد برای چند-ریپو، در دادگر صدق می‌کند

پیشنهاد صراحتاً می‌گوید: «چه موقع چند ریپو؟ اگر تیم‌های کاملاً جدا ... یا نمی‌خواهند به کد بقیه دسترسی داشته باشند». در دادگر: مدیر پروژه **صریحاً و مکتوب** خواسته بود «نه نمی‌خواهم لایه‌های وب‌سایت با موبایل یکی باشد» (CMD-012/013 → ده قانون S-1..S-10 → DOC-04 v2.0 تاییدشده). جدایی مخزنی پیاده‌سازی همان الزام مدیریت‌ی است، نه خطای ناشی از سوءتفاهم.

### ۳) نقاط قوت پیشنهاد — قابل پذیرش **بدون هیچ مهاجرتی**

| مورد پیشنهاد | ارزیابی | اقدام پیشنهادی |
|---|---|---|
| قرارداد OpenAPI به‌عنوان مرجع واحد API | **مفید و سازگار با DOC-04** (اتصال فقط از مجرای API نسخه‌بندی‌شده) | ثبت یک فایل contract نسخه‌بندی‌شده در مخزن وب + ارجاع از DOC-04؛ گسترش طبیعی D-6 |
| چک‌لیست مقیاس (stateless، CDN، صف، کش، صفحه‌بندی مکان‌نما، محدودیت نرخ، مشاهده‌پذیری، تست بار) | **سالم و استاندارد**؛ بخش بزرگی از قبل برقرار است (توابع stateless روی Vercel، Postgres مدیریت‌شده، CDN) | افزودن به نقشه‌ی راه به‌عنوان الزامات عرضی فازهای آینده |
| اعمال نقش‌ها در بک‌اند نه فقط UI | **از قبل اجرا شده** (RLS + اصلاح CMD-011) | بدون اقدام |
| اسرار فقط در Secrets / بررسی امنیتی | سالم | رعایت جاری (کلیدها هرگز وارد مخازن نشده‌اند) ادامه می‌یابد |
| فیلتر مسیر در CI و CODEOWNERS | برای تیم چندنفره معنادار است | در آینده در صورت رشد تیم |
| وب SSR (Next.js) برای سئو | نکته‌ی معتبری برای آینده‌ی وب | تصمیم جداگانه؛ مستقل از موضوع ریپو |

### ۴) تعارض‌های پیشنهاد با تصمیمات مستند و مصوب قبلی

1. **بسته‌ی مشترک design-tokens** ← مغایر S-1/S-2 (صفر فایل مشترک بین دو کلاینت — الزام صریح مدیر). توکن‌های تکراری در دو کلاینت = هزینه‌ی آگاهانه‌ی جدایی
2. **پیشنهاد React Native در صورت دانش React** ← تصمیم Flutter با ماتریس مقایسه‌ی مستند (۷۱/۵۶/۵۵) و «تایید» مدیر بسته شده (D-1/D-2)؛ پیشنهاد خودش هم می‌گوید «Flutter هم انتخاب خوبی است»
3. **Fastlane/EAS** ← M7/M8 فعلاً روی انتشار با CI فعلی و Codemagic برای iOS است؛ قابل بازنگری در همان فاز

### ۵) هزینه‌ی واقعی مهاجرت به مونوریپو (اگر مدیر بخواهد)

- **سمت موبایل: بسیار ارزان** — اسکلت ۱۳ فایلی با صفر منطق تجاری (کامیت 5e6be97)؛ ارزان‌ترین لحظه‌ی ممکن همین امروز است
- **سمت وب: متوسط و دارای ریسک** — انتقال `web/` به `apps/web` نیازمند تغییر Root Directory پروژه Vercel، مسیرهای `vercel.json`، به‌روزرسانی ۱۴ سند CMD و پیوندها؛ روی production زنده
- **سود عملی مونوریپو برای ترکیب فعلی (مدیر + اجرای AI)** محدود است: تغییرات اتمیک بین کلاینت‌ها اهمیت ندارند چون تعامل‌ها فقط از مجرای API است و قرارداد API همان نقش هماهنگی را ایفا می‌کند
- نکته‌ی صادقانه: میزبانی فیزیکی API فعلاً در بدنه‌ی مخزن وب است (توابع Vercel) — ساده‌سازی مقیاس‌پذیر فعلی؛ جداسازی آن (در هر ساختاری) در صورت رشد ممکن است

### ۶) پاسخ به پرسش پایانی پیشنهاد («تیم چه زبان‌هایی بلد است؟»)

ترکیب فعلی: مدیر + اجرای AI. مهارت‌ها: وب = JavaScript/Node (توابع serverless)، موبایل = Dart/Flutter (تصمیم مستند D-1)، دیتابیس = SQL/RLS در Supabase. تیم انسانی چندنفره وجود ندارد که ملاک انتخاب ساختار ریپو باشد.

## نتیجه

1. **«اشتباه فنی» رد می‌شود** — ساختار فعلی موجه، مستند، تازه اعتبارسنجی‌شده (CI سبز) و مطابق الزام مکتوب خود مدیر است؛ و «بک‌اند مستقل مشترک» که هسته‌ی پیشنهاد است از قبل برقرار است
2. **مونوریپو نیز انتخاب موجهی است** — تفاوت دو گزینه در گردش‌کار تیمی است نه صحت معماری
3. **سه مورد از پیشنهاد بدون مهاجرت پذیرفته می‌شود** (پیشنهاد می‌شود مدیر تایید کند): قرارداد OpenAPI، چک‌لیست مقیاس در نقشه‌ی راه، اصول Secrets/امنیت
4. **تصمیم ساختار با مدیر است — دو گزینه:**
   - **گزینه الف (توصیه‌شده):** حفظ دو مخزن + پذیرش سه مورد بالا — صفر ریسک، صفر توقف
   - **گزینه ب:** مهاجرت به مونوریپو در همین لحظه (ارزان برای موبایل، متوسط برای وب با توقف کوتاه) — فقط اگر تعامل بدون جدایی مخزنی ترجیح داده شود
