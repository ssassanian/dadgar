## متن دستور (رونوشت عینی)

> «ادامه کار»

**تفسیر ثبت‌شده (شفاف و قابل ردگیری):** مطابق الگوی دو دستور قبلی (CMD-006 با پیام «ادامه» و CMD-007 با پیام «ادامه کار»)، این پیام به‌مثابه ادامه‌ی **توالی مصوب ۸ گامی فاز ۳** است. گام‌های ۱ تا ۵ کامل و منتشر شده‌اند (v1.1.0 تا v1.5.0)؛ بنابراین «ادامه کار» = **گام ۶: اسناد (اتصال صفحه‌ی اسناد به جدول `documents` با رمزنگاری AES-256-GCM)**. این تفسیر پیش از اجرا در همین سند ثبت شد و در گزارش پایانی به مدیر اعلام می‌شود؛ در صورت تصمیم دیگر مدیر، گام‌های باقی‌مانده (۷ لاگ / ۸ CMS) به ترتیب در انتظار می‌مانند.

## محدوده‌ی دقیق اجرا (مطابق قانون عمومی — فقط همین)

1. اتصال صفحه‌ی **`cDocs`** (اسناد من — مشتری) به جدول `documents` — تنها صفحه‌ی اسناد در جدول مسیرهای مرجع (`/c/documents`).
2. چهار مسیر API جدید در لایه‌ی `web/` + فهرست سبک پرونده‌ها برای انتخابگر آپلود.
3. رمزنگاری AES-256-GCM نام فایل **و محتوای فایل** (سنگین‌ترین لایه رمزنگاری پروژه طبق مستندات خودش).
4. بدون تغییر در فایل مرجع `dadgar/` و بدون تغییر اسکیمای `web/db/schema.sql`.

## شواهد مستند (بدون گمانه‌زنی)

- **جدول `documents`** در `web/db/schema.sql` (پورت وفادار SQLite مرجع): `id, case_id(NOT NULL→cases ON DELETE CASCADE), owner_id(→users), name_enc(NOT NULL), mime, size, file(NOT NULL), created_at`
- **صفحه‌ی `cDocs`** در `dadgar/public/index.html` (فقط‌خواندنی): کارت «بارگذاری سند جدید» با dropzone نمایشی + کارت «گاوصندوق اسناد» با جدول [سند، پرونده، تاریخ، سطح دسترسی، عملیات] + دکمه‌های نمایشی «دانلود» (`data-ts`) و «حذف» (`data-md`)
- **وکیل و مدیر صفحه‌ی اسناد ندارند** در جدول مسیرهای مرجع — ولی داده‌ی نمایشیِ خودِ پروژه در گاوصندوق مشتری، «لایحه‌ی دفاعیه.pdf» را هم نشان می‌دهد ⇒ مدل پروژه: سندِ پرونده‌محور است و وکیلِ تخصیص‌یافته نیز بارگذاری می‌کند
- helperهای امنیتی موجود: `sec.encFile/decFile` (AES-256-GCM با کلید مستقل `K.file`) از فاز ۱ — دقیقاً برای همین کاربرد سندشده («files and text fields»)
- گزینه‌ی `raw` در dispatcher از ابتدا پیش‌بینی شده بود — برای آپلود باینری بدون multipart استفاده شد

## APIهای جدید (۴ مسیر + ۱ توسعه — همه با لایه‌های امنیتی فاز ۱: نشست، CSRF، نقش، نرخ، پارامتری)

| مسیر | نقش‌ها | شرح |
|---|---|---|
| `GET /api/documents` | هر سه نقش (نقش‌محور) | گاوصندوق: مشتری=اسناد پرونده‌های خودش، وکیل=اسناد پرونده‌های تخصیص‌یافته، مدیر=همه؛ با `case_title`، `mine` (بارگذارِ خودم؟) و `shared` (پرونده وکیل دارد؟) |
| `POST /api/cases/:id/documents` | client (صاحب پرونده) / lawyer (تخصیص‌یافته) | آپلود باینری خام — سقف ۴ مگابایت (413)، نام فایل در هدر `x-file-name` (URL-encoded)، سقف نرخ ۲۰/ساعت، 404 ضدافشا برای پرونده‌ی غیر خودی |
| `GET /api/documents/:id/file` | client صاحب پرونده / lawyer تخصیص‌یافته / admin | دانلود رمزگشایی‌شده — همیشه `Content-Disposition: attachment` + nosniff؛ mime با لیست سفید (غیرمجاز → `application/octet-stream`)؛ 404 ضدافشا |
| `DELETE /api/documents/:id` | بارگذارِ سند / admin | حذف — 404 ضدافشا برای بقیه (حتی صاحب پرونده برای سند وکیل) |
| `GET /api/cases?select=1` | client | توسعه‌ی سبک مسیر موجود CMD-003: فقط id/title/status پرونده‌های خود مشتری (سقف ۱۰۰) برای انتخابگر آپلود |

جمع مسیرهای API: **۴۲** (۳۸ + ۴).

## امنیت و حریم خصوصی

- **رمزنگاری در حال سکون**: `name_enc` با کلید فیلد (`aad: doc.name`) و **محتوای فایل** با کلید مستقل فایل (`sec.encFile`، `aad: doc.content`) — تست خودکار صراحتاً «plaintext نباشد» را روی دیتابیس واقعی الزام می‌کند
- **دانلود امن**: همیشه attachment (بدون رندر درون‌مرورگری) + `X-Content-Type-Options: nosniff` (سراسری) + لیست سفید mime + `Cache-Control: no-store` + نام فایل استاندارد RFC 5987 (`filename*=`)
- **حریم خصوصی**: 404 ضدافشا در آپلود/دانلود/حذف برای هر رکورد غیرمجاز؛ در گاوصندوق مشتری، اسنادِ بارگذاری وکیل دکمه‌ی حذف ندارند (فقط بارگذار یا مدیر)
- **Audit**: سه رویداد جدید `doc_upload` / `doc_download` / `doc_delete` با جزئیات پرونده/سند/حجم
- **مدیر بارگذار نیست** — `owner_id` همیشه بارگذار واقعی می‌ماند (مدیریت بدون جعل هویت)

## اصلاح انتظار یک‌خطی dispatcher (ثبت شفاف)

خواندن بدنه‌ی JSON در dispatcher سقف ثابت ۱۰۰ کیلوبایت داشت؛ برای پذیرش مسیرهای حجیم در آینده به `r.opts.bodyLimit || 100*1024` تغییر کرد (رفتار مسیرهای موجود عیناً بدون تغییر — سقف پیش‌فرض همان ۱۰۰KB). مسیر آپلود از `raw: true` (پیش‌بینی‌شده از ابتدا) استفاده می‌کند و بدنه را خودش با سقف ۴ مگابایت می‌خواند.

## تست‌ها (روی Supabase واقعی — هارنس محلی)

- **API** (`scripts/test-docs.sh` — خلاصه‌ی گروه‌ها): پاکسازی/seed ← 401 مهمان (فهرست/آپلود/دانلود) ← فهرست خالی سه نقش ← 404 پرونده‌ی ناموجود/غیرخودی ← آپلود موفق (باینری واقعی ۱۰۰ بایتی) ← بررسی plaintext نبودن در DB ← دانلود و تطابق بایت‌به‌بایت + هدرها ← فیلتر mime (text/html → octet-stream) ← پس از تخصیص وکیل: دید و دانلود وکیل + آپلود وکیل + shared=true ← سطح دسترسی استنتاجی ← 404 دانلود وکیلِ بی‌ربط ← قواعد حذف (وکیلِ بی‌ربط 404، حذف سند وکیل توسط مشتری 404، حذف توسط بارگذار و مدیر OK) ← select=1 ← آپلود پرونده‌ی بی‌وکیل توسط وکیل دیگر 404 ← رگرسیون (cases/invoices/tickets)
- **مرورگر** (`scripts/e2e-docs.py` + `run-e2e-docs.sh`): آماده‌سازی API (پرونده+پیشنهاد+تایید مدیر) ← ورود مشتری ← `/c/documents` بدون نوار زرد ← آپلود واقعی فایل از UI ← دیده‌شدن سند در گاوصندوق با حجم/سطح دسترسی درست ← دانلود واقعی و تطابق محتوا ← حذف با مودال ← نبود خطای JS
