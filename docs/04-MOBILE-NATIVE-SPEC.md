## ۰) جایگاه سند و قاعده‌ی طلایی

این سند پاسخ سه پرسش مدیریتی است: **(۱)** کدنویسی موبایل چطور انجام خواهد شد؟ **(۲)** چطور از وب کاملاً مجزا می‌ماند؟ **(۳)** بهترین حالت فنی چیست (بر اساس تحقیق از وب و منابع GitHub)؟

**قاعده‌ی طلایی (ثبت‌شده به‌دلیل نگرانی صریح مدیر در CMD-012):** وب و موبایل **دو محصول مستقل با دو کدبیس مستقل**اند که فقط از طریق یک **قرارداد API نسخه‌دار** به هم می‌رسند. هیچ فایل، ابزار، استایل، state یا اسکریپتی بین آن‌ها مشترک نیست. وب «همان‌طور که هست» ادامه می‌یابد (`فعلا اینجا در حال ساخت هستیم`) و پروژه‌ی موبایل هرگز اجازه‌ی تغییر وب را ندارد.

**بازنگری v2.1 — ظرف فیزیکی، نه ماهیت جدایی:** با تصمیم مدیر («یک ریپو باشه»، 2026-10-29) دو کدبیس مستقل در **یک مخزن واحد** (`ssassanian/dadgar`) می‌زینند: وب در `web/`، موبایل در `mobile/` — با **صفر فایل مشترک** و دو دیوار مستقل: تفکیک دایرکتوری + تفاوت زبان (Dart در برابر JavaScript). ماهیت جدایی (S-1 تا S-10) دست‌نخورده می‌ماند؛ فقط ظرف گیت از «دو مخزن» به «دو دایرکتوری ایزوله» تغییر کرد. این بازنگری پس از بررسی بی‌طرفانه‌ی CMD-015 (رد ادعای «اشتباه فنی» + شفاف‌سازی هزینه‌ی مهاجرت) و با انتخاب آگاهانه‌ی مدیر انجام شد — مونوریپو انتخاب موجهی است و تفاوت دو گزینه در گردش‌کار بود نه صحت معماری.

## ۰-۲) سابقه‌ی تصمیم — چرا سند بازنگری شد؟ (شفافیت کامل)

1. **نسخه 1.0** این سند (صبح 2026-10-29) با ماتریس وزنی خود، **React Native + Expo** را توصیه کرد؛ بزرگ‌ترین وزن آن ماتریس «هم‌زبان بودن کلاینت با بک‌اند Node.js» بود.
2. **جلسه‌ی مشاوره — چهار پیام مدیر (رونوشت عینی):**
   - «خوب توضیح کوتاه بده بتونم انتخاب کنم»
   - «پیشنهاد من: Flutter--- برای اندروید و توسعه چطوره؟»
   - «چرا کاتلین انتخاب اول نبود؟»
   - «iOS در افق برنامه دادگر هست   ر   بله هست»
3. **تحلیل بازنگری — دو ورودی مدیریتی، وزن‌های ماتریس را تغییر داد:**
   - **«iOS در افق برنامه است»**: پوشش هر دو پلتفرم با یک کدبیس از «مزیت» به **الزام** تبدیل شد. با این تصمیم، نیتیو خالص (Swift+Kotlin) به معنای دو کدبیس دائمی و هزینه‌ی دوبرابر برای همیشه است — رد شد.
   - **اولویت جدایی کامل از وب (روح CMD-012)**: هم‌خانواده بودن React Native با اکوسیستم وب (JavaScript/React) دیگر «مزیت بهره‌وری» نیست، **ریسک قاطی شدن** است — دقیقاً همان نگرانی‌ای که مدیر در CMD-012 صریحاً اعلام کرد. زبان بک‌اند (Node.js) مستقل می‌ماند و به انتخاب فریمورک کلاینت ربطی ندارد؛ هر دو کلاینت فقط با REST حرف می‌زنند.
   - **«موبایل باید نیتیو باشد»**: کامپایل AOT فلاتر به کد ماشین ARM (بدون bridge و بدون JS-runtime در زمان اجرا) نزدیک‌ترین معنا به «نیتیو» در میان گزینه‌های تک‌کدبیس است.
4. **نتیجه:** D-1 و D-2 بسته شدند — فریمورک = **Flutter**؛ سطح نیتیو = **سطح ۲ (کراس‌پلتفرم نیتیو)**؛ D-5 به‌روز شد (iOS رسماً در افق؛ زمان‌بندی پس از انتشار اندروید — بند ۱۳).

## ۴) معماری کلان

```
┌──────────────────────────┐      ┌──────────────────────────┐
│ اپ نیتیو Flutter (Dart)   │      │ اپ وب موجود (دست‌نخورده)    │
│ Android + iOS — یک کدبیس   │      │ Vercel static + serverless│
│ پوشه‌ی mobile/ مخزن dadgar  │      │ پوشه‌ی web/ مخزن dadgar    │
└────────────┬─────────────┘      └────────────┬─────────────┘
             │ HTTPS + Bearer token            │ HTTPS + Cookie (موجود)
             ▼                                 ▼
┌─────────────────────────────────────────────────────────┐
│ API مشترک — Vercel Serverless (۴۶ مسیر موجود)            │
│ + دو افزوده‌ی ثبت‌شده: /api/auth/token و /api/push/* (بند ۵)│
└──────────────────────────┬──────────────────────────────┘
                           ▼
              Supabase Postgres — ۱۶ جدول + ۱ افزوده (push_tokens)
```

- **قاعده:** تمام منطق کسب‌وکار، اعتبارسنجی، رمزنگاری AES-256-GCM و Audit سمت سرور می‌ماند. اپ موبایل فقط «کلاینت باریک نمایشی» است — همان فلسفه‌ی وب.
- **State سمت اپ:** Riverpod 3 (providers compile-safe و مستقل از BuildContext) + dio برای HTTP با interceptor توکن.
- **بدون WebView برای داده‌ی پرونده‌ها** — همه‌چیز ویجت نیتیو فلاتر.
- **لایه‌بندی:** presentation (ویجت‌ها) ← application (controllers/notifiers) ← domain (مدل‌ها و منطق خالص) ← data (api client + DTO) — الگوی Clean Architecture سبک.

## ۵) قرارداد API — دو افزوده‌ی ثبت‌شده (تنها تغییر مجاز سمت وب-سرور، با تایید مدیر)

### ۵-۱) چرا اصلاً تغییر؟
وب با کوکی+CSRF کار می‌کند (مرورگرمحور). کلاینت نیتیو مرورگر نیست — الگوی درست (منابع تحقیق) توکن Bearer است: بدون CSRF، ذخیره در Keystore/Keychain، انقضا و ابطال قابل کنترل. مسیرهای ۴۶گانه‌ی موجود عیناً دست‌نخورده می‌مانند؛ لایه‌ی security فقط باید علاوه بر کوکی، `Authorization: Bearer` را هم بپذیرد (سوییچ شفاف، سمت سرور).

### ۵-۲) افزوده‌ی اول — احراز هویت توکن
- `POST /api/auth/token` — ورودی username/password (همان حساب‌های موجود) → خروجی: `access_token` (کوتاه‌عمر، ~۱۵ دقیقه) + `refresh_token` (چرخشی، ~۳۰ روز) — ذخیره‌ی refresh روی سرور (جدول `sessions` موجود با ستون نوع/دستگاه) برای ابطال
- `POST /api/auth/token/refresh` — چرخش refresh (توکن قبلی باطل)
- `POST /api/auth/token/revoke` — خروج از همان دستگاه / ابطال همه‌ی دستگاه‌ها
- Audit: `token_issue` / `token_refresh` / `token_revoke` — نرخ‌سنجی جدا (مثلاً ۱۰/ساعت)
- OTP/SMS موجود عیناً کار می‌کند (موبایل بهترین بستر OTP است)

### ۵-۳) افزوده‌ی دوم — نوتیفیکیشن پوش
- جدول `push_tokens(user_id, platform, token, updated_at)` — افزوده‌ی ثبت‌شده با همان الگوی DDL منتظرِ settings (CMD-010) + خط `DISABLE ROW LEVEL SECURITY` (درس CMD-011)
- `POST /api/push/register` + `DELETE /api/push/register` (فقط خودِ کاربر؛ Audit `push_register`)
- ارسال: **FCM** (Firebase Cloud Messaging) با پکیج `firebase_messaging` — رویدادها: تغییر وضعیت پرونده، تایید/یادآوری نوبت، فاکتور جدید، پاسخ تیکت
- **بازگشت امن برای ایران:** گوشی‌های بدون سرویس‌های گوگل → مرکز اطلاع‌رسانی درون‌اپ (polling سبک مسیرهای موجود هنگام باز بودن اپ) — سقوط نرم، نه قطعی
- ترجیح کاربر (خاموش/روشن هر نوع رویداد) — فاز M6

### ۵-۴) قاعده‌ی نسخه‌بندی
هر تغییر ناسازگار آینده در API → مسیر `/api/v2/*`؛ مسیرهای v1 هیچ‌گاه رفتار فعلی را نمی‌شکنند (وب و اپ هر دو v1 مصرف می‌کنند).

## ۷) دیزاین‌سیستم مستقل موبایل (بدون هیچ ارثی از وب)

- **اعداد و تقویم:** اعداد فارسی با الگوی عددی `intl`؛ تقویم شمسی با پکیج `shamsi_date` — هم‌ساز با مدل زمان تهران وب (UTC+3:30)

- **الگوها:** لیست-کارت به‌جای جدول، pull-to-refresh، skeleton loading، خالی‌های صادقانه (همان صداقت وب: «داده‌ای نیست» نه داده‌ی جعلی)، Material Design 3

## ۹) تست و کیفیت (دروازه‌ی هر فاز — الگوی قانون Release)

1. **تحلیل استاتیک:** `flutter analyze` + لینت سخت‌گیرانه — دروازه‌ی اول هر PR
2. **واحد + ویجت:** `flutter_test` + mocktail — منطق api-client، نگاشت DTO، notifierها
3. **یکپارچگی:** `integration_test` روی دستگاه/شبیه‌ساز — چرخه‌های کلیدی هر ماژول
4. **e2e دستگاه:** Maestro (پشتیبانی رسمی Flutter) — سناریوی کامل مشتری←وکیل←مدیر همان سه‌ضلعی e2e وب، روی دیتابیس واقعی Supabase + پاکسازی کامل ردپا (همان انضباط صفر-ردپا)
5. **قرارداد API:** تست‌های contract — هر دو کلاینت (وب و موبایل) در برابر همان سرور باید سبز بمانند؛ شکست contract = توقف فاز
6. **دروازه‌ی انتشار:** analyze→test→integration→build→beta داخلی→production — بدون عبور از دروازه، انتشار ممنوع

## ۱۰) خط تولید و انتشار (CI/CD)

- **GitHub Actions در مخزن واحد (v2.1):** workflow `mobile-ci.yml` با فیلتر مسیر `mobile/**` و `working-directory: mobile` — PR → analyze+test؛ merge به main → بیلد AAB/APK beta (signing با keystore خارج از مخزن) → توزیع داخلی؛ تگ `M-x.y.z` → بیلد prod. تغییرات `web/` هرگز این workflow را اجرا نمی‌کند و دیپلوی Vercel وب از پوشه‌ی `web/` مستقل است.
- **iOS بدون مک:** Codemagic — بیلد ابری مک و انتشار App Store/TestFlight (سند رسمی Codemagic) — فعال‌سازی پس از تصمیم D-7
- **Google Play:** internal testing → closed testing (لیست بسته‌ی مدیر) → production (رول‌اوت تدریجی)
- **انتشار در ایران:** علاوه بر Play — APK امضاشده‌ی مستقیم (صفحه‌ی دانلود وب) و کافه‌بازار؛ نسخه‌ها بایت‌به‌بایت همان بیلد prod
- **OTA (اختیاری):** سنجش Shorebird در M7 برای پچ Dart بدون بازنشر فروشگاهی — فقط با تایید مدیر (D-4 مکمل)
- **کلید امضا:** keystore هرگز در مخزن نیست؛ محل نگهداری در دفتر کلیدها ثبت می‌شود (KEY-۰۰۳+)
