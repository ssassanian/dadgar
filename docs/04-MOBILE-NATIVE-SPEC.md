## ۰) جایگاه سند و قاعده‌ی طلایی

این سند پاسخ سه پرسش مدیریتی است: **(۱)** کدنویسی موبایل چطور انجام خواهد شد؟ **(۲)** چطور از وب کاملاً مجزا می‌ماند؟ **(۳)** بهترین حالت فنی چیست (بر اساس تحقیق از وب و منابع GitHub)؟

**قاعده‌ی طلایی (ثبت‌شده به‌دلیل نگرانی صریح مدیر در CMD-012):** وب و موبایل **دو محصول مستقل با دو کدبیس مستقل**اند که فقط از طریق یک **قرارداد API نسخه‌دار** به هم می‌رسند. هیچ فایل، ابزار، استایل، state یا اسکریپتی بین آن‌ها مشترک نیست. وب «همان‌طور که هست» ادامه می‌یابد (`فعلا اینجا در حال ساخت هستیم`) و پروژه‌ی موبایل هرگز اجازه‌ی تغییر وب را ندارد.

## ۵) قرارداد API — دو افزوده‌ی ثبت‌شده (تنها تغییر مجاز سمت وب-سرور)

### ۵-۱) چرا اصلاً تغییر؟
وب با کوکی+CSRF کار می‌کند (مرورگرمحور). کلاینت نیتیو مرورگر نیست — الگوی درست (منابع تحقیق) توکن Bearer است: بدون CSRF، ذخیره در Keychain/Keystore، انقضا و ابطال قابل کنترل. مسیرهای ۴۶گانه‌ی موجود عیناً دست‌نخورده می‌مانند؛ لایه‌ی security فقط باید علاوه بر کوکی، `Authorization: Bearer` را هم بپذیرد (سوییچ شفاف).

### ۵-۲) افزوده‌ی اول — احراز هویت توکن
- `POST /api/auth/token` — ورودی username/password (همان حساب‌های موجود) → خروجی: `access_token` (کوتاه‌عمر، ~۱۵ دقیقه) + `refresh_token` (چرخشی، ~۳۰ روز) — ذخیره‌ی refresh روی سرور (جدول `sessions` موجود با ستون نوع) برای ابطال
- `POST /api/auth/token/refresh` — چرخش refresh (توکن قبلی باطل)
- `POST /api/auth/token/revoke` — خروج/ابطال همه‌ی دستگاه‌ها
- Audit: `token_issue` / `token_refresh` / `token_revoke` — نرخ‌سنجی جدا (مثلاً ۱۰/ساعت)
- OTP/SMS موجود عیناً کار می‌کند (موبایل بهترین بستر OTP است)

### ۵-۳) افزوده‌ی دوم — نوتیفیکیشن پوش
- جدول `push_tokens(user_id, platform, token, updated_at)` — افزوده‌ی ثبت‌شده با همان الگوی DDL منتظرِ settings (CMD-010)
- `POST /api/push/register` + `DELETE /api/push/register` (فقط خودِ کاربر؛ Audit `push_register`)
- ارسال: Expo Push Service — رویدادها: تغییر وضعیت پرونده، تایید/یادآوری نوبت، فاکتور جدید، پاسخ تیکت
- ترجیح کاربر (خاموش/روشن هر نوع) در جدول settings هر کاربر — فاز M6

### ۵-۴) قاعده‌ی نسخه‌بندی
هر تغییر ناسازگار آینده در API → مسیر `/api/v2/*`؛ مسیرهای v1 هیچ‌گاه رفتار فعلی را نمی‌شکنند (وب و اپ هر دو v1 مصرف می‌کنند).

## ۷) دیزاین‌سیستم مستقل موبایل (بدون هیچ ارثی از وب)

- **زبان و راستا:** فارسی، RTL کامل — `I18nManager.forceRTL(true)` + ویژگی‌های منطقی (`start/end` به‌جای left/right) + شماره‌ی فارسی
- **فونت:** Vazirmatn (وزن‌های 400/500/700) — باندل‌شده در اپ، هیچ وابستگی به وب
- **پالت:** هویت مستقل موبایل (پیشنهاد: پس‌زمینه‌ی روشن گرم + آبی-سرمه‌ای حقوقی + accent سبز تایید؛ تم تیره در M7) — نهایی‌اش با تایید مدیر (D-3)
- **ناوبری:** Bottom Tabs پنج‌تایی مشتری (خانه/پرونده‌ها/نوبت/فاکتور/پروفایل) + استک برای جزئیات؛ نقش وکیل و مدیر تب‌های خودشان را می‌بینند (همان سه نقش وب)
- **الگوها:** لیست‌کارت به‌جای جدول، pull-to-refresh، skeleton loading، خالی‌های صادقانه (همان صداقت وب: «داده‌ای نیست» نه داده‌ی جعلی)

## ۹) تست و کیفیت (دروازه‌ی هر فاز — الگوی قانون Release)

1. **واحد:** Jest + @testing-library/react-native — منطق api-client و reducerها
2. **e2e دستگاه:** Maestro (yaml ساده، پایدار) — سناریوی کامل مشتری←وکیل←مدیر همان سه‌ضلعی e2e وب
3. **قرارداد API:** تست‌های contract مشترک — هر دو کلاینت در برابر همان دیتابیس واقعی Supabase
4. **دروازه‌ی انتشار:** lint→test→build(EAS)→beta داخلی→production — بدون عبور از دروازه، انتشار ممنوع
5. **پاکسازی:** همان انضباط صفر-ردپا (کاربران تست و داده‌ها حذف کامل)

## ۱۰) خط تولید و انتشار (CI/CD)

- **GitHub Actions** در مخزن جدا: PR → lint/test؛ merge به main → EAS Build (beta) + نصب داخلی؛ تگ `M-x.y.z` → بیلد prod + ارسال به Play Console
- **Play Console:** internal testing → closed testing (لیست بسته‌ی مدیر) → production (رول‌اوت تدریجی) — اولین نسخه فقط اندروید (D-5 برای iOS/App Store — نیاز به حساب Apple و ملاحظات تحریم/انتشار ایران)
- **OTA:** اصلاحات JS با EAS Update بدون بازنشر فروشگاهی (در محدوده‌ی مجاز پلی‌استور)
